# BizScan 记忆架构

本文说明当前 BizScan 项目的记忆架构、数据存放位置、读写流程和保护策略。对应主要代码：

- `backend/chat_memory.py`
- `backend/agents/query_agent.py`
- `backend/main.py`
- `backend/config.py`

## 总体分层

当前记忆分为三类：

```text
业务长期记忆 Business Memory
对话长期记忆 Chat Long-term Memory
短期会话记忆 L0/L1/L2
```

业务长期记忆回答“系统对公司和行业客观知道什么”。对话长期记忆回答“这个 chat_id 关心什么、偏好什么、纠正过什么”。短期会话记忆回答“当前会话刚才聊了什么”。

## 业务长期记忆

业务长期记忆是全平台共享的行业和公司资料，主要由日报 Agent 和档案 Agent 写入。

存储位置：

```text
data/companies/{company_name}/*.md
data/companies/_index.json
data/digests/*.md
data/analysis/*.json
data/raw_news/
data/insights/
data/keyword_report/
```

主要来源：

- `smart_digest_agent.py`：采集新闻、分析、生成日报。
- `profile_update_agent.py`：生成或更新公司 10 模块档案。
- `query_agent.py`：通过工具读取业务记忆，原则上不直接写业务文件。

典型工具：

```text
read_company_analysis(company_name, module_name?)
read_daily_digest(digest_date)
start_company_analysis(company_name)
web_search(query, recency_days)
```

记忆优先级上，客观公司事实以业务长期记忆、日报、搜索工具返回为准，优先于聊天记忆。

## 对话长期记忆

对话长期记忆按 `chat_id` 隔离。群聊和单聊都优先使用 `chat_id`；只有 `chat_id` 为空时才 fallback 到 `user_id`。

存储位置：

```text
data/chat_memory/chats/{chat_id}/
```

目录结构：

```text
MEMORY.md
watchlist.md
preferences.md
corrections.md
workflow_state.md
references.md
```

各 topic 含义：

| 文件 | 用途 |
| --- | --- |
| `MEMORY.md` | 长期聊天记忆索引，每轮注入给模型 |
| `watchlist.md` | 当前 chat 长期关注的公司、关键词、赛道 |
| `preferences.md` | 回复风格、称呼、篇幅、日报推送等偏好 |
| `corrections.md` | 用户纠正过的名称、别名、口径 |
| `workflow_state.md` | 跨会话仍有效的进行中任务 |
| `references.md` | 常查资料、链接、外部资料入口 |

### MEMORY.md 索引

`MEMORY.md` 是轻量索引，不是完整记忆正文。每轮对话都会读入并放进模型上下文。

示例：

```md
# Chat Memory Index

本文件是长期聊天记忆的短索引，每轮可注入上下文。正文请按需读取 topic 文件。

- [watchlist.md](watchlist.md) — 群关注公司/主题；宇树科技、智元机器人
- [preferences.md](preferences.md) — 回复风格、日报推送和篇幅偏好；回答前先说“你好，尊贵的女士”
- [corrections.md](corrections.md) — 纠错、别名、口径修正；晨昏线正确称呼为晨昏线公司
- [workflow_state.md](workflow_state.md) — 跨会话仍有效的进行中任务；暂无记录
- [references.md](references.md) — 常查资料和外部指针；暂无记录
```

索引摘要来自各 topic 文件正文的前一小段，目前在 `_summarize_topic_file()` 中截取约 120 字。

### 长期记忆写入流程

长期聊天记忆通过 `write_chat_memory(topic, operation, item, reason)` 写入。

流程：

```text
1. 校验 topic 是否属于预定义 topic
2. 校验 operation 是否为 add/update/remove
3. ensure_chat_memory(chat_id)，确保目录和 topic 文件存在
4. 写入对应 topic 文件
5. 检查 topic 文件大小，必要时打 warning 埋点
6. rebuild_memory_index(chat_id)，同步重建 MEMORY.md
```

一次写入会更新：

```text
data/chat_memory/chats/{chat_id}/{topic}.md
data/chat_memory/chats/{chat_id}/MEMORY.md
```

严格顺序是先写 topic，再重建索引。当前锁粒度是 `chat_id + topic`，不是整个 `chat_id` 全局锁。

### 长期记忆读取策略

每轮固定注入：

```text
MEMORY.md
preferences.md 正文，如果有内容
corrections.md 正文，如果有内容
```

按需工具读取：

```text
watchlist.md
workflow_state.md
references.md
```

保留 `read_chat_memory(topic)` 工具，模型在需要 topic 正文时仍可主动读取。

`preferences.md` 和 `corrections.md` 被每轮自动注入，是因为它们通常属于“每轮必须遵守”的规则。例如：

```text
回答前先说“你好，尊贵的女士”
不要把晨昏线公司写成晨昏线科技
```

这样可以避免每轮都让模型先决定是否调用 `read_chat_memory`，降低延迟并提高稳定性。

## 短期会话记忆

短期记忆按 `chat_id` 存储，用于处理当前会话上下文和指代。

存储位置：

```text
data/chat_sessions/{chat_id}/current.json
```

字段：

```json
{
  "chat_id": "...",
  "last_active": "...",
  "round_count": 0,
  "last_compact_at": "...",
  "rounds_since_compact": 0,
  "session_summary": "...",
  "recent_messages": []
}
```

### L0 当轮上下文

L0 是一次 `handle_user_query()` 内的临时上下文，包括：

```text
当前 messages
ToolMessage
搜索结果
日报全文
公司档案全文
```

L0 不落盘。函数结束后即丢弃。

### L1 recent_messages

L1 是最近原文消息，写在 `current.json` 的 `recent_messages` 中。

用途：

```text
刚才说的是哪家公司？
它再详细点
上面那个公司呢？
```

写入时：

- user 消息保存 `user_id`、`content`、`ts`。
- assistant 回复截断到 1200 字。
- `tool_digest` 截断到 800 字。
- 工具全文不写入短期 JSON。

### L2 session_summary

L2 是滚动摘要，写在 `current.json` 的 `session_summary` 中。

compact 触发条件：

```text
recent_messages 超过 12 轮对应消息量
或当前短期上下文超过 8000 字
或距离上次 compact 已增加 6 轮
```

compact 行为：

```text
旧 session_summary + 较早 messages -> 新 session_summary
保留最近 8 轮原文
清理更早原文
更新 last_compact_at
rounds_since_compact 归零
```

摘要要求在 prompt 中约束为四段：

```text
话题
涉及公司
未完成事项
关键结论
```

## 每轮 Query 上下文栈

每轮给模型的上下文大致顺序是：

```text
1. SystemPrompt
2. MEMORY.md 索引
3. 自动注入的 preferences.md / corrections.md 正文
4. session_summary
5. recent_messages
6. 当前用户 HumanMessage
7. 当轮 ToolMessage 循环
```

其中 `ToolMessage` 属于 L0，不会完整落盘。

## 保护策略

### 短期会话 TTL

启动 FastAPI 时会执行：

```text
cleanup_expired_chat_sessions()
```

默认配置：

```env
CHAT_SESSION_TTL_DAYS=30
```

30 天未活跃时只删除：

```text
data/chat_sessions/{chat_id}/current.json
```

不会删除：

```text
data/chat_memory/chats/{chat_id}/
```

因此长期偏好、纠错、关注列表仍会保留。

### 长期 topic 大小 warning

默认配置：

```env
CHAT_MEMORY_TOPIC_WARNING_BYTES=20480
```

在 topic 读、写、重建索引时检查文件大小。超过阈值只打 warning 埋点，不自动删除。

这样可以先发现长期记忆增长问题，避免误删用户记忆。
